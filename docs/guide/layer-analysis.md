# Layer Analysis

This page records the source-derived responsibility layers, not directory names. It answers where each layer lives, where its configuration schema is declared, where its dedicated wire protocol is defined, where its user-facing copy is mounted, which store owns its state, and who calls it through which channel.

## Layer map

### L1 Contract and rules

- **Responsibility**: define business shapes, state transitions, sampling, pricing, and analytics vocabulary without depending on ASP.NET Core, EF Core, MySQL, or Redis.
- **Implementation**: entities and rules live in `server/src/Doggo.Domain` — for example users in `server/src/Doggo.Domain/Users/UserEntities.cs`, orders in `server/src/Doggo.Domain/Orders/OrderEntities.cs`, cases in `server/src/Doggo.Domain/Cases/CaseEntities.cs`, and price crawling in `server/src/Doggo.Domain/Price/PriceCrawlEntities.cs`.
- **Configuration schema**: `AnalyticsEventDictionary` declares event and property whitelists at `server/src/Doggo.Domain/Analytics/AnalyticsEventDictionary.cs:13`; `AnalyticsOptions` defines event retention at `server/src/Doggo.Infrastructure/Analytics/AnalyticsOptions.cs:4`.
- **Protocol/copy**: none. Wire DTOs belong to L3; UI copy belongs to L6.
- **State/call surface**: no owning store. `Doggo.Api`, `Doggo.Worker`, `Doggo.Scraper`, and `Doggo.PriceCrawler` consume these types, while `Doggo.Infrastructure` references them through its project graph at `server/src/Doggo.Infrastructure/Doggo.Infrastructure.csproj:14`.
- **Lifecycle**: compiled into every server host; stateless types and pure rules are initialized at process start.

### L2 Persistence and application services

- **Responsibility**: own transaction boundaries, EF mappings, cross-table use cases, external Steam/OpenID/WeChat clients, and operational invariants.
- **Implementation**: `DoggoInfrastructureExtensions` registers MySQL and Redis at `server/src/Doggo.Infrastructure/DoggoInfrastructureExtensions.cs:11`; `DoggoDbContext` exposes domain sets and the audit override at `server/src/Doggo.Infrastructure/Persistence/DoggoDbContext.cs:15`; application services include `OrderService` at `server/src/Doggo.Infrastructure/Orders/OrderService.cs:55`, `GroupBuyingService` at `server/src/Doggo.Infrastructure/Cases/GroupBuyingService.cs:33`, `RollService` at `server/src/Doggo.Infrastructure/Cases/RollService.cs:31`, and `MarketStore` at `server/src/Doggo.Infrastructure/Market/MarketStore.cs:19`.
- **Configuration schema**: `ConnectionStrings:Default` and `ConnectionStrings:Redis` are read at `server/src/Doggo.Infrastructure/DoggoInfrastructureExtensions.cs:17`; `AuthOptions` is declared at `server/src/Doggo.Infrastructure/Auth/AuthOptions.cs:7`; `VaporOptions` is declared at `server/src/Doggo.Infrastructure/Vapor/VaporOptions.cs:4`; `WechatOptions` is declared at `server/src/Doggo.Infrastructure/Auth/WechatSessionClient.cs:21`; invitation and check-in options are declared at `server/src/Doggo.Infrastructure/Marketing/InviteOptions.cs:5` and `server/src/Doggo.Infrastructure/Marketing/SignOptions.cs:5`.
- **Protocol/copy**: none.
- **State/call surface**: MySQL owns authoritative business and analytics state; Redis owns the Vapor webhook idempotency claim at `server/src/Doggo.Infrastructure/Vapor/WebhookIdempotencyStore.cs:51`; no news, market, product, user, order, or analytics state is kept in process memory. L3 and L4 call application services in-process; L2 calls MySQL through EF Core, Redis through StackExchange.Redis, and Steam/OpenID, WeChat, or Vapor through HTTP.
- **Lifecycle**: registered as a scoped `DoggoDbContext` and scoped use-case services by each host; Vapor and webhook idempotency clients are HTTP client or singleton dependencies; MySQL rows survive redeployment, while a failed Redis claim falls back to a process-local claim.

### L3 Service orchestration

- **Responsibility**: expose one independently deployable REST surface for browser, miniapp, mobile, and admin traffic; authenticate requests; enforce endpoint authorization; record visits; orchestrate application services.
- **Implementation**: `Program` composes security, clients, and stores at `server/src/Doggo.Api/Program.cs:25`; endpoint maps and prefixes begin at `server/src/Doggo.Api/Program.cs:139`; `VisitLogMiddleware` writes a request row in a `finally` block at `server/src/Doggo.Api/VisitLogMiddleware.cs:13`; authorization and admin role requirements are wired in endpoint maps such as `server/src/Doggo.Api/Endpoints/AdminEndpoints.cs:27`.
- **Configuration schema**: `AuthOptions`, `WechatOptions`, `VaporOptions`, `InviteOptions`, and `SignOptions` bind their sections in `server/src/Doggo.Api/Program.cs:29`; OpenAPI is exposed only in Development at `server/src/Doggo.Api/Program.cs:125`.
- **Protocol/copy**: the public protocol is REST and lives in endpoint files, not one schema file. Groups include `/api/auth`, `/api/products`, `/api/orders`, `/api/group-buyings`, `/api/roll`, `/api/events`, and `/api/admin`; `/api/vapor/webhook` defines the inbound Vapor protocol at `server/src/Doggo.Api/Endpoints/VaporEndpoints.cs:10`; no static UI copy is mounted here.
- **State/call surface**: mostly stateless. It reads MySQL for simple back-office queries and calls L2 for transactional use cases; the analytics ingest limiter is intentionally process-local at `server/src/Doggo.Api/Endpoints/EventEndpoints.cs:195`. Web and admin call it as same-origin HTTP; miniapp and mobile call it with JSON plus bearer tokens through shared code at `shared/src/client.ts:112`. Vapor pushes signed webhooks; a failed handler releases the Redis idempotency claim so delivery can retry.
- **Lifecycle**: one ASP.NET Core host. Startup builds DI and routing; requests are authenticated, authorized, visit-logged, mapped, and returned; `/healthz` checks MySQL and Redis at `server/src/Doggo.Api/Program.cs:153`; Docker Compose runs a one-shot migrator before the API starts at `deploy/docker-compose.prod.yml:35`.

### L4 Scheduling and async work

- **Responsibility**: independently drive delayed and periodic work without blocking request threads or depending on an API instance being alive.
- **Implementation**: `Doggo.Worker/Program` registers all loops at `server/src/Doggo.Worker/Program.cs:18`. `MarketSyncWorker` polls the Vapor job API at `server/src/Doggo.Worker/Market/MarketSyncWorker.cs:17`; `OrderTimeoutWorker`, `OrderReconciliationWorker`, `RollRoomWorker`, `CoinExpiryWorker`, `FunnelAggregateWorker`, and `AnalyticsRetentionWorker` begin at `server/src/Doggo.Worker/Orders/OrderTimeoutWorker.cs:10`, `server/src/Doggo.Worker/Orders/OrderReconciliationWorker.cs:13`, `server/src/Doggo.Worker/Cases/RollRoomWorker.cs:10`, `server/src/Doggo.Worker/Marketing/CoinExpiryWorker.cs:10`, `server/src/Doggo.Worker/Analytics/FunnelAggregateWorker.cs:12`, and `server/src/Doggo.Worker/Analytics/AnalyticsRetentionWorker.cs:13`.
- **Configuration schema**: sections bound at `server/src/Doggo.Worker/Program.cs:21`: `Vapor`, `Market:Sync`, `Order`, `Roll`, `Coin`, `Analytics`, `Invite`, and `Sign`.
- **Protocol/copy**: none. Its outbound Vapor API protocol is shared with L2 in `server/src/Doggo.Infrastructure/Vapor/VaporClient.cs:40`.
- **State/call surface**: stateless loops delegate to L2; every durable result is MySQL. Market sync calls Vapor over HTTP, while other loops issue query/update calls to MySQL. No UI channel calls L4 directly.
- **Lifecycle**: one .NET `BackgroundService` host. Startup binds options and registers hosted services; each loop keeps its own interval or due-time gate; the shared deployment is always-on and independent of API, Scraper, and frontends at `deploy/docker-compose.prod.yml:90`.

### L5 External ingestion

- **Responsibility**: acquire external news and third-party price observations, normalize and clean them, enforce scheduling and compliance controls, then persist durable series or articles.
- **Implementation**: one `Doggo.Scraper` process hosts news and price crawling. The host registers news adapters, stores, schedulers, and Playwright at `server/src/Doggo.Scraper/Program.cs:11`; it then mounts the price crawler at `server/src/Doggo.Scraper/Program.cs:38`. The news worker starts at `server/src/Doggo.Scraper/ScraperWorker.cs`; RSS, Steam App News, and HTML adapters start in `server/src/Doggo.Scraper/News/Adapters`. The price worker begins at `server/src/Doggo.PriceCrawler/PriceCrawlerWorker.cs:18`, adapters and ingest/scheduler live beside it, and its admin review endpoint is mounted by the API at `server/src/Doggo.PriceCrawler/PriceCrawlerAdminEndpoints.cs:23`.
- **Configuration schema**: `Scraper` values are bound at `server/src/Doggo.Scraper/Program.cs:31`; defaults live in `server/src/Doggo.Scraper/appsettings.json:8`. `PriceCrawlerOptions` is declared at `server/src/Doggo.PriceCrawler/PriceCrawlerOptions.cs:67` and bound at `server/src/Doggo.PriceCrawler/PriceCrawlerServiceCollectionExtensions.cs:18`.
- **Protocol/copy**: no user-facing protocol. Adapter inputs are RSS/Atom, Steam App News JSON, generic HTTP HTML, and robots.txt; robots handling is implemented in `server/src/Doggo.PriceCrawler/Robots/RobotsChecker.cs:58`. Its `/api/admin/price-crawl/maps` management surface is registered into L3 by `server/src/Doggo.PriceCrawler/PriceCrawlerAdminEndpoints.cs:23`.
- **State/call surface**: MySQL owns news sources/items, crawl maps, raw captures, cleaned series, and per-site state; there is no Redis or in-memory durable store. It calls HTTP news and price sources; L3 calls its management endpoints, and Admin reads those through the L3 route at `admin/src/pages/Settings/index.tsx:191`.
- **Lifecycle**: one always-on worker process in production. `NewsSourceSeeder` seeds sources, the news scheduler loops, the price worker and scheduler run separately, raw captures expire by retention, and the process is independent of API and Worker at `deploy/docker-compose.prod.yml:75`.

### L6 Client experience

- **Responsibility**: provide platform-specific user and operator journeys, retain local presentation/session state, and translate actions into the REST contract.
- **Implementation**: web entry is `web/src/main.tsx:11`; admin entry is `admin/src/app.tsx:14`; miniapp and RN apps initialize shared client identity at `miniapp/src/app.ts:11` and `mobile/src/app.ts:17`. Web pages live under `web/src/pages`; admin pages live under `admin/src/pages`; Taro pages live under `miniapp/src/pages` and `mobile/src/pages`.
- **Configuration schema**: web uses `VITE_API_BASE` at `web/src/api/client.ts:12`; Taro uses `TARO_APP_API_BASE` at `shared/src/client.ts:8`; admin proxies same-origin `/api` through its runtime config at `admin/nginx.conf:20` and production reverse proxy at `deploy/nginx/doggo.conf.template:29`.
- **Protocol/copy**: route-level page copy is mounted inside each app source tree; admin operation copy is colocated with page components. The browser protocol is JSON REST with same-origin cookies at `web/src/api/client.ts:40`; the Taro protocol adds bearer tokens and `X-Doggo-Client` at `shared/src/client.ts:116`; web analytics batches share the event shape at `web/src/api/events.ts:123`, while Taro apps queue batches through `shared/src/events.ts:92`. There is no REST schema file shared by all clients.
- **State/call surface**: web and admin keep no durable UI store and send same-origin cookies; localStorage holds only the analytics session/channel/queue at `web/src/api/client.ts:88`. Miniapp and mobile keep tokens, cache, and analytics queues in Taro storage, with an injectable adapter at `shared/src/client.ts:30`; mobile replaces broken RN sync storage at `mobile/src/storage.ts:8`. All four call L3 over HTTPS. Admin additionally consumes `/api/admin/*`; Vapor is not called directly by clients.
- **Lifecycle**: each is separately built and served. Compose serves web and admin as static Nginx images dependent on the API at `deploy/docker-compose.prod.yml:105`; miniapp and mobile are independently packaged and initialized at app startup.

### L7 Runtime surfaces and shared client library

- **Responsibility**: supply databases/cache, migrations, proxies/static hosting, and the single Taro client implementation reused by miniapp and RN.
- **Implementation**: MySQL and Redis are deployed at `deploy/docker-compose.prod.yml:7`; the migration job is at `deploy/docker-compose.prod.yml:35`; web/admin proxies and containers are configured at `deploy/nginx/doggo.conf.template:19`, `web/nginx.conf:1`, and `admin/Dockerfile:1`. `@doggo/shared` is implemented in `shared/src/client.ts:8`, `shared/src/endpoints.ts`, and `shared/src/events.ts:1`.
- **Configuration schema**: database names and credentials come from Compose environment at `deploy/docker-compose.prod.yml:1`; proxy upstreams come from templates at `deploy/nginx/doggo.conf.template:29`; shared client API base and storage behavior come from app code described under L6.
- **Protocol/copy**: MySQL wire protocol, Redis command protocol, HTTP reverse proxy, container orchestration, and the internal TypeScript API are the relevant protocols. MySQL/Redis/Compose have no user copy; `@doggo/shared` carries endpoint request/response interfaces at `shared/src/endpoints.ts`.
- **State/call surface**: MySQL and Redis own their volumes; Nginx is stateless; Taro storage is the L6 persistence seam. API/Scraper/Worker call MySQL and Redis; browsers and Taro clients call Nginx or L3; shared code is imported by miniapp and mobile via workspace links at `miniapp/package.json` and `mobile/package.json`.
- **Lifecycle**: MySQL and Redis run from named volumes; migration runs once before API; Nginx containers run with API dependency; shared code is built into each consuming Taro bundle rather than independently deployed.

## Why this decomposition

1. **Separate invariants from deployment I/O.** Domain types and pure rules compile into every server host but cannot bind EF, MySQL, or ASP.NET Core. This is visible in the reference graph: `Doggo.Domain` has no package references at `server/src/Doggo.Domain/Doggo.Domain.csproj:1`, while Infrastructure introduces MySQL and Redis at `server/src/Doggo.Infrastructure/DoggoInfrastructureExtensions.cs:34`.
2. **Use one transaction owner per business operation.** Application services own the scoped `DoggoDbContext`, business writes, and audit side effects rather than allowing endpoints to invent transactional behavior. `AnalyticsRecorder` deliberately joins the caller's save batch at `server/src/Doggo.Infrastructure/Analytics/AnalyticsRecorder.cs:13`, and `OrderService` owns state changes around `server/src/Doggo.Infrastructure/Orders/OrderService.cs:55`.
3. **Keep request orchestration independently scalable and stateless.** The API host binds no durable queue or UI store; it reads simple projections and delegates transactional work. Scaling API instances therefore does not split business state, and `/healthz` explicitly checks both backing services at `server/src/Doggo.Api/Program.cs:153`.
4. **Decouple periodic work from request latency and API availability.** Market jobs, order timeouts/reconciliation, roll draws, coin expiry, funnel aggregation, and retention each run as `BackgroundService` loops registered at `server/src/Doggo.Worker/Program.cs:48`; removing the API cannot stop these compensations, and deployment makes Worker a separate process at `deploy/docker-compose.prod.yml:90`.
5. **Isolate untrusted source acquisition and compliance.** Retry, circuit breaking, robots, timeouts, and site concurrency differ from normal request handling. Price crawl configuration explicitly carries retry/circuit/robots/site policies at `server/src/Doggo.PriceCrawler/PriceCrawlerOptions.cs:71`, while news source failure and circuit state are persisted in `server/src/Doggo.Scraper/News/ScraperScheduler.cs:47`.
6. **Keep client experience platform-specific behind one wire contract.** Web uses cookies, Taro uses storage plus bearer tokens, and each app can choose its build/runtime stack while calling the same REST surface; the shared Taro client explicitly injects storage because RN behaves differently at `shared/src/client.ts:23`. This avoids forcing React DOM, Ant Design Pro, WeChat, and RN into one runtime.
7. **Own shared runtime resources once, at the deployment surface.** Database/cache credentials, migration ordering, proxy routing, and container dependencies are declared together at `deploy/docker-compose.prod.yml:35`; application code must not invent environment-specific connection or startup ordering. A shared Taro client is also preferable to duplicating request/auth/event behavior because miniapp and mobile intentionally reuse it at `miniapp/src/api/endpoints.ts:5`.
